Event-driven post-call architecture

~5M messages / day

Every call ends in work: billing, live metrics, uploading the recording, AI analysis, customer webhooks. Before this design, five call flows each did that work inline and in their own way. A slow S3 upload or a customer's webhook endpoint could hold up the dialer, and billing logic existed in five copies.

Publishers fire and forget. Each consumer has its own queue, its own retry policy and its own failure store.

What I did

  • Designed the architecture and moved all five call flows onto one RabbitMQ topic exchange, with routing keys per flow and per event.
  • Split fast lanes (billing, metrics) from slow lanes (S3, AI, webhooks) so the dialer never waits on a consumer.
  • Shipped the first flow myself, then led the team through migrating the other four and mentored 3 junior developers along the way.

Correctness under failure

  • Idempotent billing handlers with atomic credit deduction, so a redelivered message never charges twice. These replaced five duplicated billing implementations.
  • Per-queue retries through a delayed-message exchange, and a failed-events store for replay. Events no longer disappear silently.

Predictive dialer, built from scratch

10K → 500K calls/day · 750K peak

A predictive dialer calls leads before an agent is free and connects only the calls that get answered. Dial too little and agents sit idle. Dial too much and calls drop, or one tenant uses up the carrier capacity that every other tenant shares.

Rate limits are enforced at a shared choke point, so a noisy campaign can't starve other tenants.

What I did

  • Designed and built the dialer from scratch: campaign and lead management, the pacing controller, and call control over Asterisk ARI.
  • Built per-tenant rate and concurrency limits in Redis to protect the shared calling APIs and carrier capacity.
  • Added fan-out across many PBX nodes with dynamic publishers and consumers, so capacity grows by adding nodes.

Scaling 50×

  • Load-tested with a purpose-built campaign harness, then tuned timeouts, listener lifecycles and limiter thresholds.
  • Fixed memory leaks in the hot path and added PBX health alerts and a stale-call reconciler so stuck calls can't hold capacity or leave balances unsettled.
  • Took it from 10K to 500K calls/day, with a peak of 750K.

AI call quality analysis

Every recorded call, analysed

QA teams could only spot-check a small fraction of calls by hand. The goal was to transcribe and score every call, using each customer's own QA rubric, without the AI provider's latency or outages affecting call handling.

Three flows feed one hardened consumer. Each organisation's settings decide how its calls are analysed.

What I did

  • Built the module: Whisper transcription of every call, with GPT-4o summaries, sentiment, keywords and rubric Q&A.
  • Made it multi-tenant by configuration: each organisation has its own prompt template and transcription mode, so onboarding a new QA rubric needs no code change.
  • Built the React dashboards QA managers use to browse the results.

Reliability

  • An atomic claim means the consumer, the reconciler, manual retries and resets can't process the same job twice.
  • Bounded concurrency protects the provider rate limits. A DLQ and a reconciler recover stuck jobs.
  • Customers can choose to defer their call-completed webhook until the analysis is ready, so their CRM receives one complete payload.

Real-time AI voice bots & voice streaming

100K+ streamed calls/day · 200K peak

To make phone calls conversational, live call audio has to leave the PBX, reach a speech-to-text, LLM and text-to-speech loop, and come back fast enough to sound natural. The bot also has to stop talking the moment the caller interrupts.

Streaming at every stage, with first audio returned before the LLM has finished its response.

What I did

  • Built the streaming STT → LLM → TTS pipeline and connected the Asterisk PBX to bots over WebSockets, with barge-in.
  • Built the voice-streaming service for incoming and outgoing calls. It now carries 100K+ calls/day.

Production hardening

  • Added client-side and server-side stream metrics (packet interval, clock drift, low-network detection) so audio problems can be diagnosed rather than guessed at.
  • Added event reconnection, health checks and alerting, and fed post-call events into the shared exchange.

Reports product, conceived and built solo

Peak memory flat at ~350 MB · 10–30 s → ms

Large tenants (350K+ calls/day) crashed exports with out-of-memory errors, and the dialer latency report took 10–30 seconds to load. Managers had no self-serve way to export what they needed.

Separately, p50/p90/p99 dialer latency is precomputed every 5 minutes, so the report reads a small rollup instead of scanning raw calls.

What I did

  • Owned the product end to end, solo: requirements, the React UI, the Node.js backend and delivery.
  • Built call and agent productivity reports (talk, wrap-up, idle and disposition time) with filters, async generation, live progress, presigned S3 downloads and email delivery.

Performance

  • Streamed exports from a MongoDB cursor through CSV and gzip into S3 with Node.js backpressure. This fixed the OOM crashes and kept peak memory at about 350 MB.
  • Precomputed percentile rollups cut the latency report's load time from 10–30 s to milliseconds. Aggregation and index tuning sped up the remaining reports.
